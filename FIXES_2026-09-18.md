# Fixes — 2026-09-18

## 1. Discount badge overlapping the product name (root cause, site-wide)
`frontend/tailwind.config.ts` was missing `./ui.tsx` from its `content` array.
`ui.tsx` is where `ProductCard`, `Header`, `Footer`, price tags, etc. all
live, so Tailwind's JIT compiler was silently dropping every utility class
used *only* there — including the "X% OFF" badge's `absolute bottom-2
left-2` positioning. The badge rendered with no positioning at all and sat
on top of the product name. **Fixed** by adding `./ui.tsx` to `content`.
This one line was very likely responsible for other subtle layout issues
across the site too, not just the badge — do a full visual pass after
deploying this.

## 2. Broken-image "logo" on the homepage
`frontend/app/page.tsx`'s hero image used a raw `<img src={heroImage}>`
instead of the app's own `<SafeImage>` component (used everywhere else),
so a relative/failed path rendered the browser's broken-image icon instead
of falling back to a placeholder. **Fixed** by switching to `<SafeImage>`.

## 3. Register / Login failing
The code path (Firebase email/password + backend sync) was correct, but
errors were swallowed into one generic message. **Fixed** by surfacing the
real Firebase error code and adding specific messages for the most likely
causes: `auth/operation-not-allowed` (Email/Password sign-in not enabled
in Firebase console), `auth/invalid-api-key` / `auth/configuration-not-found`
(bad/missing `.env.local` values), `auth/unauthorized-domain`, and
`auth/network-request-failed`. Also separated "Firebase account created,
backend sync failed" as its own case with the real backend error message.
**Action needed on your end:** confirm `.env.local` has real values from
Firebase Console → Project Settings → Your apps, and that Email/Password
is enabled under Authentication → Sign-in method. I reproduced
`auth/invalid-api-key` locally with a blank/placeholder config, which
matches your symptom exactly.

## 4. Admin panel "accessible without login"
Checked this in detail: every `/admin/*` page already gates rendering on
`useAdminSession()`, and the backend's `AdminAuthFilter` enforces
`admin=true` server-side on every `/api/admin/**` call. This is not
actually an open door. The one real (and already documented in the code)
weakness is that the backend currently trusts the raw Firebase UID as a
bearer token instead of verifying a real Firebase ID token — see the
comment block in `Auth.java`'s `FirebaseAuthService`. Wiring up real
Firebase Admin SDK token verification is a separate, larger change and
was intentionally left alone per that file's own "Stage 1" note.

## 5. Cancel order
Already existed end-to-end (frontend button + backend block once
SHIPPED/OUT_FOR_DELIVERY/DELIVERED). No change needed — it's just nested
inside the collapsed order row on `/account`, which may be why it looked
missing.

## 6. Return window (10 days after delivery) — new feature
Did not exist at all before. Added:
- `Order` entity: `deliveredAt`, `returnStatus`, `returnRequestedAt`,
  `returnReason` (`Orders.java`).
- `deliveredAt` is now stamped automatically the *first* time an admin
  sets an order's status to DELIVERED (`Admin.java`), and never
  overwritten after that.
- `PUT /api/orders/{orderId}/return` — customer requests a return; only
  allowed while status is DELIVERED and within `ReturnStatus.WINDOW_DAYS`
  (10) of `deliveredAt`.
- `PUT /api/admin/orders/{id}/return-status` — admin approves / rejects /
  marks a return completed.
- `OrderDto` now includes `deliveredAt`, `returnStatus`,
  `returnRequestedAt`, `returnReason`, `returnEligible`,
  `returnWindowEndsAt` so the frontend never has to compute the window
  itself.
- Frontend: `/account` now shows a "Return this order" button with a
  "closes in N days" hint while eligible, plus the current return status.
  `/admin/orders` shows a return-status pill and Approve/Reject/Complete
  buttons.
- `database/004_stage_returns.sql` added for environments that don't rely
  on `ddl-auto=update`.
